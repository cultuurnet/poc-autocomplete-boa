# Benchmark query set for the MySQL vs Elasticsearch address autocomplete POC.
#
# One query per line. Blank lines and lines starting with '#' are ignored,
# duplicates are dropped by the runner so no query is weighted twice in the
# pooled latency aggregate.
#
# These are not random queries. Every section below is a case where the two
# engines are expected to behave differently, because a query set where both
# engines score the same tells you nothing. All names, postcodes and localities
# are real and present in openaddress-bevlg.csv.

# --- Progressive prefixes ---------------------------------------------------
# What a type-ahead actually receives: one request per keystroke. The short
# prefixes are the expensive ones (huge candidate sets, ranking decides
# everything) and the long ones are the cheap ones. Latency on "g" and quality
# on "goorbaan" are two different questions and both matter.
g
go
goo
goor
goorb
goorba
goorbaa
goorbaan
k
ke
ker
kerk
kerks
kerkstraat

# --- Street plus municipality -----------------------------------------------
# Two tokens that live in different fields of the same document. MySQL has to
# match both against one FULLTEXT haystack; Elasticsearch can use a
# cross_fields or multi_match. This is the bread-and-butter query shape.
goorbaan herselt
korte lindenstraat aalst

bondgenotenlaan leuven

# --- Street plus postcode ---------------------------------------------------
# A numeric token next to a name. Tokenisers that drop or split digits, and
